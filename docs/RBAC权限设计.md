# RBAC 权限设计

- 版本：V1.0
- 日期：2026-10-21
- 适用需求：[需求规格说明书](./需求规格说明书.md)

## 1. 授权原则

采用用户—角色—权限的 RBAC 模型，叠加工单数据范围与状态约束：

> 允许操作 = 已认证且账号有效 ∧ 角色拥有操作权限 ∧ 满足工单数据范围 ∧ 满足状态及输入条件。

角色权限不能单独保障“只看自己的工单”，必须检查 `requester_id` 或当前 `assignee_id`。默认拒绝未明确授予的操作，授权在后端实施。

首期三种角色，无隐含管理员、无角色继承；协调员没有其他角色的全部权限。首期一个账号一个角色，数据库保留多对多关系便于未来演进，多角色分配当前不开放。

## 2. 角色与权限矩阵

“本人”指原提交者，“当前负责”指当前 assignee_id 等于登录用户 ID。

| 权限码 | 操作 | REQUESTER | COORDINATOR | SUPPORT |
| --- | --- | --- | --- | --- |
| ticket:create | 创建工单 | 允许 | 禁止 | 禁止 |
| ticket:read:own | 查询本人提交的工单 | 允许 | — | — |
| ticket:read:all | 查询全部工单 | — | 允许 | — |
| ticket:read:assigned | 查询当前负责工单 | — | — | 允许 |
| ticket:comment | 补充信息或回复 | 本人、未完成 | 全部未完成 | 当前负责、未完成 |
| ticket:category:update | 纠正分类 | 禁止 | 未完成 | 禁止 |
| ticket:assign | 首次分派 | 禁止 | 未完成 | 禁止 |
| ticket:reassign | 转派 | 禁止 | 未完成 | 禁止 |
| ticket:start | 开始处理或返工 | 禁止 | 当前负责，待处理或返工 | 当前负责，待处理或返工 |
| ticket:result:submit | 提交处理结果 | 禁止 | 当前负责，处理中 | 当前负责，处理中 |
| ticket:confirm | 确认完成 | 本人，待确认完成 | 禁止 | 禁止 |
| ticket:rework | 要求返工 | 本人，待确认完成 | 禁止 | 禁止 |
| ticket:history:read | 查看全部公开历史 | 本人 | 全部 | 当前负责 |
| ticket:related:create | 新建时关联旧工单 | 本人已有的已完成工单 | 禁止 | 禁止 |
| attachment:upload | 上传临时图片 | 允许 | 禁止 | 禁止 |
| attachment:bind | 创建或补充时绑定图片 | 本人上传，本人工单未完成 | 禁止 | 禁止 |
| attachment:read | 读取图片 | 本人工单；本人未过期临时图片 | 全部已绑定工单图片 | 当前负责工单图片 |
| notification:read | 查询通知和未读数 | 本人有效通知 | 本人有效通知 | 本人有效通知 |
| notification:mark-read | 标记已读 | 本人通知 | 本人通知 | 本人通知 |

“—”表示不授予该范围权限，用户可以通过本角色其他 read 权限访问对应范围。已完成后的 read 和 history:read 仍然可用，全部写权限受只读规则限制。

上述矩阵将三种角色的业务操作分离，员工提交由 REQUESTER 执行。未来如需同一人兼任支持与提交者，应先明确角色切换或多角色授权语义，再开放用户角色配置。

## 3. 数据访问规则

### 3.1 提交者

- 列表查询必须包含 `requester_id = current_user.id`。
- 详情、沟通、历史、验收、返工和关联目标检查同一归属条件。
- 编号可预测也不能绕过归属校验。

### 3.2 协调员

- 可以读取全部工单，操作受权限码、状态及输入校验限制。
- 可以在本人为当前处理人时开始处理及提交结果；不能以可读全部代替当前处理人条件，不能确认完成或要求返工。
- 分派目标必须是账号有效且具有 SUPPORT 或 COORDINATOR 角色的用户，允许协调员选择本人领取；候选仅返回 ID、显示名和角色。
- 可以读取只包含必要字段的支持人员候选列表，这不是用户管理或角色管理权限。
- 协调员转派出去后仍保留全局读取和协调权限，但失去该工单的开始处理与提交结果资格。技术支持转派出去后失去该工单读取和写入权限。

### 3.3 技术支持

- 列表查询必须包含 `assignee_id = current_user.id`。
- 详情和所有写入均重新核对当前处理人，不以历史参与过或创建过回复作为访问依据。
- 转派后原支持人员失去详情、历史和写入权限，不能凭旧页面或旧登录会话继续操作。
- 转派生效之后的请求必须遵循新归属；已经读取的内容不能从用户记忆或本地缓存中收回。

### 3.4 关联与元数据

- 关联关系不传递授权。读取旧工单时再次检查旧工单本身的归属权限。
- 若当前用户无权读取关联目标，不返回其原文、回复或处理结果，不提供可访问的详情预览。
- 汇总、计数、搜索、候选列表和历史接口同样需要权限控制。

## 4. 服务端实现约束

- Spring Security 管理登录会话和基础接口认证，Service 层执行操作权限、数据归属和状态校验。
- 服务端从会话加载当前用户、有效状态及权限；前端传入的 role、requester_id 等不能覆盖服务端身份。
- DTO 使用字段白名单，创建时禁止接收状态、处理人、提交人等可被批量赋值的敏感字段。
- 每个业务动作使用明确接口，例如开始处理、提交结果、确认、返工；不暴露任意状态修改接口。
- 列表在 SQL 查询时约束范围，不先查全量再在页面过滤；写入在事务中验证最新归属及状态。
- 使用行锁或带版本与归属条件的原子更新，并确保沟通写入也与转派正确串行，防止检查通过后发生转派仍写入。
- 工单变更和对应事件在同一事务内提交；提交结果与返工原因均必须非空白。
- request_id 的幂等返回也检查提交者身份，唯一约束异常不可直接回传数据库错误。
- 账号、角色和权限通过受控初始化建立，不开放注册或角色变更 API。

## 5. 前端行为与错误语义

- 页面按服务端返回的可执行动作显示按钮，减少无效操作，但不替代后端授权。
- 未认证：401；已认证但不具备该操作权限：403。
- 对超出数据范围的工单详情或子资源，统一返回 404，不区分不存在与无权读取。
- 合法状态冲突、版本过期、request_id 冲突：409；格式或必填校验失败：400。
- 优先完成身份、动作及归属校验，再返回状态冲突细节，避免通过错误信息泄露数据。
- 分派、完成确认及返工成功后刷新工单版本与可执行动作。

## 6. 必测权限场景

1. 未登录不能查询或修改工单。
2. 提交者 A 不能读取 B 的详情、历史、回复，也不能通过关联编号访问 B 的工单。
3. 提交者不能调用分派、纠正分类、开始处理或提交结果接口。
4. 协调员可以查看全部和分派，但不能替代提交者验收。
5. 技术支持不能访问未分派或分派给其他人的工单。
6. 转派后原支持人员的直接 API 请求被拒绝，新支持人员能读取完整公开历史。
7. 前端篡改角色和用户 ID 不改变后端权限。
8. 已完成工单对所有角色只读。
9. 并发转派与旧支持人员写入不会造成越权提交。
10. 无权读取旧工单的人员不会因新工单关联而获得旧工单内容。
11. 其他提交者使用已有 request_id，不获得原工单及提交人信息。
12. 图片经后端代理读取并检查当前工单归属；原技术支持转派后不能通过旧附件 ID 读取图片，MinIO 桶禁止匿名访问。
13. 图片绑定必须核对上传者，不能将其他用户临时图片绑定到自己的工单；已完成工单不可补图。
14. 通知查询与已读只能操作本人通知，通知中的关联不能绕过工单授权。

## 7. 后续扩展

未来增加系统管理员时，独立定义用户管理和角色分配权限，不默认授予工单正文读取权。部门或服务组隔离属于数据范围扩展，需要调整查询和对象授权，不能仅增加角色名。权限配置页面、多人兼任角色、授权变更失效机制和权限审计在后续迭代中单独设计。
